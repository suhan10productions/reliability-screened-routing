# Publication-readiness assessment after the matched-comparison revision

## Completed in this revision

- Every original configuration is compared on the common 46 instances, with
  paired probability and resource intervals.
- Uniform padding is explicitly called conservative-speed planning. Its
  deterministic on-time guarantee is explained as a property of construction.
- The conservative-speed generator is screened with the same buffer grid and
  service admission rule, with all-instance fallback reporting.
- Individual direct-reachability caps are tested without changing offered
  promises or rerunning identical candidate models.
- A two-pass clock-profile-aware approximation has a disclosed search budget,
  exact deterministic rescheduling, and visible missing-output counts.
- All 21 original failures receive a per-instance reachability audit. Search
  failure is not automatically labelled infeasibility, and passing a necessary
  test is not automatically labelled proof of feasibility.
- Scheduled duration and simulated route duration are distinguished.
- The clock-origin explanation is in reproducibility, initialization is
  disclosed, and the absolute-distance solver gap remains visible.
- Every method receives fresh validation draws, with a separate fixed-plan
  parameter sweep. Reuse of the synthetic instance set is acknowledged.
- Source code, protocol, results, generated tables, and validation checks are
  included. The 17-reference audit is preserved.

## Remaining before a venue-specific submission

1. Select a target venue and apply its template, length, disclosure,
   anonymization and data/code requirements.
2. Have a domain reviewer assess novelty against the closest service-level
   routing and self-imposed-window literature. The contribution is a
   replaceable, auditable procedure with mechanism comparisons, not a new
   exact stochastic optimizer.
3. Strengthen external validity with established VRPTW benchmark families or
   a public/operational road network. HGS on the same synthetic instances is
   a solver-quality check, not external validation.
4. For an operational claim, calibrate disruption parameters locally and
   evaluate against an independent instance set. Weight and admission-bank
   size sensitivity remain incomplete.
5. Confirm authorship spelling, affiliations, acknowledgment permissions and
   applicable AI-assistance disclosures. The retained author spelling is
   unchanged pending confirmation.

6. Timestamp `CONFIRMATORY_PROTOCOL.md` with `FROZEN_MANIFEST.json` publicly,
   then run it once and report every hypothesis, whatever its outcome.
7. After that, test external validity on an established benchmark family or
   an independent instance generator. New seeds from the same generator test
   repeatability within one distribution only.
8. Before release: remove internal version labels from file names, remove
   correspondence details, and archive code and data with a durable DOI.

The research is ready for a focused methodological review. It does not yet
support deployment in commercial dispatch without calibration and field
validation.
