# Reliability-screened routing: research code and evidence archive

**Naming note.** The project's earlier working name was "routeops". The code
modules are now named `relscreen_v5`, `relscreen_v6` and `relscreen_v7`. The
`"schema"` identifiers inside result files (for example
`"routeops-v7-instance-1"`) are data-format tags and are deliberately unchanged,
so that the archived records remain byte-identical to the original runs and new
runs stay format-compatible with them.

The manuscript and raw records implement the fixed protocol in
`EXPERIMENT_PROTOCOL_V7.md`. The revision corrects mixed-denominator
comparisons, renames uniform padding as conservative-speed planning, tests
screening with that generator, adds reachability-capped contractions and a
clock-aware approximation, and distinguishes no-plan outcomes from proven
infeasibility. Historical result files are immutable inputs.

## Recreate the analysis and PDF

Use Python 3.12, the pinned requirements, and a LaTeX distribution with
`latexmk`. From this directory:

```bash
python -m venv .venv
.venv/bin/pip install -r requirements.txt
PYTHONPATH=code .venv/bin/python -m unittest discover -s tests -v
PYTHONPATH=code .venv/bin/python code/verify_v7.py
PYTHONPATH=code .venv/bin/python code/analyse_v7.py
cd paper
latexmk -pdf -interaction=nonstopmode -halt-on-error routing_model_v7.tex
```

The scalar v6 evaluator is preserved. The vectorized v7 evaluator uses exactly
the same speed integral and arc-specific random streams; tests and the
integrity script compare them against archived outcomes. Numerical changes in
the main old-plan results come from the fresh validation bank, not a changed
travel model.

## Regenerate the added experiments

Write to a new empty output directory when rerunning. The driver resumes by
instance filename and does not overwrite completed records. The analysis reads
`results/v7/`; retain the original records before changing that location.

```bash
PYTHONPATH=code OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 \
  .venv/bin/python code/study_v7.py \
  --inputs results/study_v6_n20.json results/study_v6_n50.json \
           results/study_v6_n100.json results/study_v6_n200.json \
  --output results/v7_rerun --workers 6 --seconds 5
```

The new methods retain five-second search limits, at most three attempts when
no plan is returned, and the first feasible result. A reachability certificate
permits skipping an impossible contracted model. The clock approximation uses
two 2.5-second matrix solves in addition to its already-computed nominal seed
plan. Wall-clock-limited local search can vary across hardware or load; use
the retained raw records to reproduce the exact manuscript tables.

The original five-second records and equal-budget HGS benchmarks are included
with their original driver code. They are not regenerated by the v7 analysis.
The capped variant deliberately reuses candidates when the contracted model
is unchanged, preventing a rerun of the same model from being mistaken for a
contraction effect. Scenario seeds are 100000+instance for screening,
400000+instance for fresh validation, and 500000+instance for the fixed-plan
parameter sweep. Each plan is selected before the new validation bank is
instantiated. Revising a protocol after inspecting outcomes requires a new
label and an explicit explanation.

## Interpretation

The fixed conservative speed pads all travel, including off-peak travel. It
is not a fully time-dependent baseline. The separate clock-aware approximation
uses predicted departure times and rejects routes that fail exact
deterministic rescheduling. Missing outputs remain visible.

The 46-instance matched results are conditional on conservative-speed plan
availability. All-instance procedure results include fixed fallbacks. Planned
driver time and simulated route duration are reported separately. The
parameter sweep evaluates fixed plans; it does not recalibrate or re-screen
them for each cell. New scenario draws do not turn this reused synthetic
instance set into an external test set.

This is a research implementation for synthetic delivery-fleet instances, not
a validated dispatch system. Real road networks, calibrated disturbance
parameters, heterogeneous vehicles, replanning and operator validation remain
outside the model.

## Confirmatory study (proposed, not yet run)

`CONFIRMATORY_PROTOCOL.md` specifies four directional hypotheses, their tests,
decision rules and failure policy for 53 fresh instances (instance seeds
shifted by 60000). It discloses one pilot smoke test, on an instance outside
that set. The protocol is proposed until it is publicly timestamped together
with `FROZEN_MANIFEST.json`, which `code/freeze_manifest.py` writes.

`code/confirm_analysis.py` has two modes. `confirmatory` validates the complete
prescribed study (seed set, run parameters, scenario counts, seed derivations,
stage-1 to stage-2 provenance, and the frozen manifest) before computing
anything, and is the only mode that prints a verdict. `descriptive` accepts any
records, including the development set, and labels its output descriptive.

`study_v6.py --seed-shift 0` (the default) reruns the development design;
wall-clock solver limits can produce different routes. Use the archived records
to reproduce the exact reported tables. Both drivers record outcomes per configuration: a solver returning no
plan is recorded as `no_plan`, a configuration whose prerequisite has no plan
as `not_attempted`, and successful configurations are always kept. Any other
exception is recorded as a software error with its traceback and is never
scored; confirmatory analysis refuses to run while one exists.

`code/check_confirmatory_safeguards.py` demonstrates the safeguards: a
complete synthetic study and a per-configuration failure study pass, and
17 tampering or failure cases are rejected. These relabelled fixtures are
software checks, not fresh experimental evidence.

`code/ahp_weights.py` reproduces the AHP weights and consistency ratio from
the pairwise-comparison matrix given in the manuscript's appendix.
